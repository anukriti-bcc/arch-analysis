# Real ADRs: how do the benchmarks compare with real practice?

Every benchmark in this project is generated by the team. This check collects **real** Architecture Decision Records from public
repositories and measures three things the synthetic data cannot: how often a real ADR says anything about which parts of a system
may depend on each other, whether the code-only reader (M6) can read the ones that do, and how the relevance matcher behaves on real text.
First written 2026-11-16, last updated 2026-11-22 (includes the team verification of the sample labels and the 7-case model run). **Exploratory: not pre-registered**, see "How the sample was chosen" for the decisions made along the way.

## Summary (read the caveats below before quoting any number)

1. **ADRs that govern dependencies between parts of a system are rare.** In a random sample of 60 real ADRs, with labels of record that are AI-drafted and
   verified row by row by the team, **3 (5.0%, 95% CI 1.7% to 13.7%)** clearly govern dependencies and **10 (16.7%, CI 9.3% to 28.0%)** do at least partly
   (see "Human verification"; the earlier single-pass read gave 2 and 6). Most ADRs record technology and process choices (a library, a cloud service, a
   release scheme). Conformance checking against ADRs applies to a small slice of real ADRs.
2. **The code-only reader (M6) could not read the dependency-governing ones.** On the 6 found in the first read, it returned "unclear" for 4 and "permits" for 2; it never
   produced a sensible restriction, even for "the rest of the codebase **never imports** `opentelemetry` directly" (its prohibition cues lack "never").
   This is a sample of 6, but the held-out result (M6 matched M7) does not carry over to real dependency rules.
3. **Real ADRs describe categories, not named files.** They say "modules", "bounded contexts", "the rest of the codebase". The benchmark's ADRs name files
   in backticks (primary, held-out) or describe a module by purpose (hard tier, some cases). Matching an ADR to a particular flagged import is a
   scope-resolution problem the benchmarks barely exercise.
4. **The benchmark's central scenarios do not appear in the sample.** Date-limited grandfathering is rare (dates appear in the decision text of
   2.5% of ADRs; none of the 6 dependency-governing ones had a cut-off date) and no sampled ADR names a module and carves out a
   dated exception. The nearest real examples are irregular: one ADR says modules should not depend on each other, then "we allow direct calls in the
   future, but this should be an exception, not a rule".
5. **The relevance matcher rarely over-selects, but it under-selects.** For typical type pairs it selected 0.5% to 6% of real ADRs (table below), so
   over-firing is small in absolute terms here. It requires the exact word, so "Controllers" and "databases" never match; accepting plurals would
   add matches (controller -> repository: 3 ADRs to 5 of 202; service -> database: 7 to 10). These counts are small, so the direction is the finding, not the size.
6. **A defect in M6 was found by real text**: for MADR-format ADRs (12.9% of this corpus) the frozen reader takes "Decision Drivers" as the decision
   section. The benchmarks never used that layout. M6 is frozen and was not changed; a corrected finder is used for this analysis only
   (`experiments/real_adrs/profile.py`), and a test documents the defect.

**What this does to the project's claims.** The strongest defensible reading: the methods work where an ADR states a rule about a named module (benchmarks),
that situation is uncommon in real ADRs, and real dependency-governing ADRs are plain or irregular prose that a convention-based code reader did not
handle (6 cases). It is **not** shown that M7 reads real ADRs well: the only model run on real ADR text is the 7-case study below, where M7 scored 5 of 7, the same as always answering "violation", with two scope errors and one over-generalisation. A model has not been run on the 60-ADR sample or any larger set.

## How the sample was chosen (every decision is a bias)

* **Source.** GitHub repository search by topic (`architecture-decision-records`, `adr`, ..., plus architecture-themed topics with at least 30 stars),
  and 18 well-known projects listed by hand (`datasets/curated_adr_projects.txt`). ADR files are markdown files in a directory named `adr`/`adrs` or
  containing `decision`, with a numbered, dated or `adr-` file name; README/template/index files are excluded. At most 25 ADRs per repository (seeded random) so one
  repository cannot dominate; at least 5 ADRs per repository.
* **First attempt, discarded as the main corpus.** Run with no date filter, the search returned mostly 2025-26 repositories about ADRs for AI coding agents
  (median 2 stars, many ADR tools, probably machine-written records). Nothing from that run was used to choose between methods. The rule was then fixed
  *before looking at any dependency-related result*: only repositories **created before 2023-01-01** (before LLM-assisted writing), tool/template/teaching
  repositories excluded by name, curated well-known projects added. That first sample is kept separately (`datasets/real_adrs_agent_era`,
  `results/real_adrs_agent_era`) and is not used for any claim here.
* **A second fix after a poor yield.** The first ADR-folder pattern missed `architecture-decision-record/` and `Architecture-Decision-Log/`, and a size filter
  rejected Backstage although blobless clones download nothing. The pattern was broadened and the size filter removed (tests in `tests/test_real_adrs.py`).
* **Result:** 1,123 candidate repositories, 400 examined, **16 had at least 5 ADRs; 11 are projects (not ADR tools) and form the main corpus: 202 ADRs**
  (4 boilerplate "record architecture decisions" files excluded). Most architecture-themed repositories simply do not keep ADRs (384 of the 400 had fewer than 5).

* **Biases to keep in mind.** Topic-tagged, mostly well-known projects; those that bother to tag or keep ADRs are probably more disciplined than average;
  English; markdown ADRs in conventional folders only; 11 repositories is a small number and a few (Dapr, Backstage, Protean) contribute many ADRs;
  Protean's ADRs date from 2026 (the creation-date filter applies to the repository, so later records can be machine-assisted).
* **Licences and redistribution.** ADR texts belong to their authors and are **not** committed (`datasets/real_adrs/corpus/` is git-ignored; re-create with
  `python -m experiments.real_adrs.fetch_corpus`). The repository publishes the manifest (repo, path, commit SHA, licence, SHA-256 of each file),
  the analysis, and short excerpts (at most 900 characters) in the annotation sheet, taken only from permissively licensed repositories, with source URLs.

## Findings in detail

**Corpus profile (202 ADRs, 11 repositories).** Format: 76.7% Nygard-like (Context/Decision/Consequences), 12.9% MADR-like, 10.4% other.
A decision section is found in 91.6%; 44.1% carry a date; median length 289 words; 14.9% use
exception-like words (exception, temporary, legacy, migration, ...) in the decision; **2.5% contain a calendar date in the decision text;
0% contain a relative time limit** ("within 30 days", "by the end of Q3"), so the date-limit machinery of M7 would almost never be exercised on this corpus.

**Prevalence of dependency-governing ADRs.** Measured by reading, not by the keyword proxy.
The keyword proxy (`rule_tier`) flagged 1.0% as an explicit dependency rule and 17.3% as weaker, but on the first hand-read sample its
**precision was 0.33 and recall 0.67**, so its percentages overstate the prevalence by roughly 2 to 3 times and should not be quoted. The 60-ADR sample was labelled in three stages:

| Stage | Clearly (yes) | At least partly (yes or partly) |
|---|---|---|
| First read (single AI pass, `indicative_labels_claude.csv`) | 2 of 60 (3.3%, CI 0.9% to 11.4%) | 6 of 60 (10.0%, CI 4.7% to 20.1%) |
| Second AI pass, blind to the first (`annotation_sheet_claude_pass2.csv`) | 3 of 59 (5.1%) | 11 of 59 (18.6%) |
| **Team-verified labels of record** (`annotation_sheet_verified.csv`) | **3 of 60 (5.0%, CI 1.7% to 13.7%)** | **10 of 60 (16.7%, CI 9.3% to 28.0%)** |

Quote the last row. The two stages before it are kept for the record (see the next two sections).

The two clear cases of the first read: an ADR enforcing "explicit boundaries between modules ... prevent direct coupling across unrelated domains" (general, no names), and
"all OpenTelemetry interaction is funneled through a single module; the rest of the codebase never imports `opentelemetry` directly" (a precise, checkable
allow-list rule).

**Code-only reader (M6) on the six of the first read (frozen code).** stance "unclear" for 4, "permits" for 2, "prohibits" for 0. Overall on the corpus M6 returns a stance for
38% of ADRs (17.8% prohibits, 20.3% permits), but most of those ADRs are not about dependencies at all, so a
stance is not evidence of understanding. (In the pipeline M6 first requires a strong scope match, which real ADRs rarely satisfy because they do not name files.)

**Relevance matcher (`find_relevant_adrs`, type words only, project code unchanged) on 202 real ADRs.**

| Flagged dependency types | Selected by the matcher as written | If plurals were accepted (sensitivity only) |
|---|---|---|
| controller -> repository | 1.5% | 2.5% |
| service -> database | 3.5% | 5.0% |
| controller -> database | 0.5% | 0.5% |
| ui -> database | 1.0% | 1.0% |
| domain -> infrastructure | 5.9% | 5.9% |
| api -> database | 5.9% | 6.4% |
| handler -> repository | 2.0% | 2.0% |
| view -> model | 2.0% | 2.0% |

## What was NOT done (so nobody assumes it was)

* A language model was run only on the 7 hand-built cases below, not on the 60-ADR sample or any larger set, so nothing here measures how well M5/M7 read real ADRs at scale.
* No real repository was checked for conformance against its own ADRs: the dependency-governing ADRs found are mostly general and would need rules
  written for them by hand.
* One sample of 60 from 11 repositories, labelled by an AI draft and verified by the team. Percentages have wide intervals; differences between repositories are not analysed.
* The 2025-26 AI-agent-era sample was profiled by the same code (tier shares 6.4% / 13.8% / 79.9%, 51% "unclear" for M6) but is not validated and is not used.

## Second labelling pass (2026-11-21) and who did what

The team initially did not have time to label the sample. Rather than leave it single-rater, a **second, separate AI pass** was done: Claude labelled
all 60 excerpts in `results/real_adrs/annotation_sheet_claude_pass2.csv` **without opening the first pass's labels**, and the two were compared
afterwards (`results/real_adrs/agreement_claude_pass1_vs_pass2.json`). **Both passes are AI labels** (the team verification that followed is described in "Human verification" below; the pass files still say AI-only). They are not independent in the strong sense: the same model family, the same
instructions, and the same author context wrote the analysis code.

| | Pass 1 (`indicative_labels_claude.csv`) | Pass 2 (blind to pass 1) |
|---|---|---|
| Clearly about dependencies (yes) | 2 of 60 (3.3%) | **3 of 59 (5.1%, 95% CI 1.7% to 13.9%)** (R006 has no decision text and is unlabelled) |
| At least partly (yes or partly) | 6 of 60 (10%) | **11 of 59 (18.6%, CI 10.7% to 30.4%)** |

Agreement between the passes: 59 compared, raw 3-class 0.90, **kappa 0.61**; dependency-or-not (yes/partly vs no): raw 0.92, **kappa 0.66**.
All 6 disagreements are borderline calls between "partly" and "no" (R003, R013, R040, R042, R043) or "yes" and "partly" (R034). The robust
conclusion is unchanged and is stated as a range: **dependency-governing ADRs are a small minority (roughly 3% to 19% depending on how
"partly" is counted)**. Q2 and Q3 were labelled in pass 2 only and have not been compared with anything.

## Human verification (2026-11-22): AI draft, verified by the team

The team reviewed all 60 rows of `review_sheet_for_human_verification.xlsx` (AI pass-2 labels shown; the reviewer agrees by leaving the cell empty, corrects by choosing a label).
All 60 rows are marked done. Ingested with `experiments/real_adrs/ingest_review.py` into `results/real_adrs/annotation_sheet_verified.csv` and
`verification_summary.json`. **These verified labels are now the labels of record**; the files say "AI draft (Claude), verified row by row by a human reviewer".

| | Result |
|---|---|
| Q1 labels the reviewers **changed** | 1: R013 partly to no ("just library choice for http fetching, not a module dependency rule") |
| Q1 supplied where the AI left it blank | 1: R006 (decision file is empty on GitHub) labelled no; Q2 no |
| Q2 changed | 1: R048 no to yes ("at that moment / move later if needed") |
| Q3 changed | 0 |
| The 6 rows where the two AI passes disagreed | Reviewers kept the pass-2 label on 5 (R003, R034, R040, R042, R043) and sided with pass 1 on 1 (R013) |
| AI draft vs final Q1 | 58 of 59 identical (raw 0.98, kappa 0.94 three-class); **not inter-rater agreement, see "Provenance" below** |
| Prevalence, clearly about dependencies (yes) | **3 of 60 (5.0%, 95% CI 1.7% to 13.7%)** |
| Prevalence, at least partly (yes or partly) | **10 of 60 (16.7%, CI 9.3% to 28.0%)** |

**Provenance.** All 60 rows were verified by the team members themselves, independently of the AI that drafted the labels, and the review is recorded under all three names (Kartik Agarwal, Kush Singh, Anukriti Chauhan; the sheet has one shared name field, so individual rows are not attributed to individual members). Two earlier review sheets were wrong and were discarded; this sheet is the one of record. The reviewers did make real changes (R013, R048, and R006 supplied) and resolved the 6 rows where the two AI passes disagreed. Two reviewer notes show reasoning (R013, R048).

**How to describe it.** "AI-drafted, verified row by row by the team." One limit remains and should be stated: the sheet displayed the AI draft beside each excerpt, so the 0.94 kappa between draft and final labels measures how often the reviewers confirmed the draft, not agreement between two labellers working from scratch. The sample is also one team's judgment of a sample the same team built. The robust statement is: **dependency-governing ADRs are a small minority, roughly 5% (clear) to 17% (including partly)**.

**Optional extra: a small blind check.** `results/real_adrs/blind_check_for_human.xlsx` has 20 excerpts in shuffled order (all 11 rows the AI labelled yes or
partly plus 9 random "no" rows), no AI labels shown, and two cells for the reviewer's name and whether they used an AI assistant (about 15 minutes, one person, no AI
assistance). `python -m experiments.real_adrs.ingest_blind_check --sheet <file> --key ../results/real_adrs/blind_check_key.csv --pass2 ../results/real_adrs/annotation_sheet_claude_pass2.csv --out ../results/real_adrs`
reports agreement and kappa with the AI labels, and flags the result incomplete if the name or declaration is missing. Positives are oversampled, so it measures agreement, not
prevalence. It is not required for the labels of record; if it is run, results can add "and a blind check of 20 rows (kappa X)". (The key file must not be given to the reviewer.)

## Case study: 7 hand-built cases from real ADRs (time-boxed; M7 run 2026-11-22, results below)

`datasets/real_adrs_case_study/cases.csv`, runner `experiments/real_adrs/case_study.py`. Four real ADRs (Protean ADR-0008, modular-monolith-with-ddd ADR-14,
ADNC ADR-001, educational-platform ADR-12; all MIT or Apache-2.0), each **pinned to a commit and a SHA-256** (the runner refuses text that does not match),
with a hand-written flagged dependency and a draft expected verdict. **This is a demonstration, not a benchmark:** seven cases cannot give a rate. The
expected verdicts are a **draft written by the person who built the cases**; two are marked `debatable` (C04, C06); all seven were reviewed by the team before any result was quoted
(`reviewed_by_team`, `team_expected` columns; see "Finishing the real-ADR part").

**M6 on the seven (frozen code, no model needed), run 2026-11-18:**

| | Result |
|---|---|
| Reading only (the ADR is forced in) | "unclear" for 6 of 7; "permits" for C04 (the modular-monolith ADR: "we allow direct calls in the future, but this should be an exception"), which is the wrong way round. **0 of 7 read correctly.** |
| As the pipeline runs it (the relevance matcher must select the ADR first) | The ADR is selected for only 2 of 7 (C01, C02, because the Protean ADR names the files). **M7 on the seven:** run 2026-11-22 (7 model calls, Qwen2.5 7B Q4); results and a critical reading follow. Caveats: seven cases, expected verdicts drafted by the case builder, one small quantised model.

## Case study results (M7 reading of real ADR text, run 2026-11-22; `results/real_adrs_case_study/`)

Setup: the ADR text is given to M7's extractor directly (reading only), against the 7 verdicts that Anukriti Chauhan wrote before seeing the draft or any
model output (self-reported) (7 of 7 agree with the draft; `cases_reviewed.csv`). Same model as the benchmark (Qwen2.5 7B Q4).

| Case | Truth | M6 as pipeline | M6 reading only | M7 | M7's reason, read critically |
|---|---|---|---|---|---|
| C01 | justified | violation | unclear | violation | **Wrong.** Says the ADR prohibits imports in "utility modules" and `telemetry.py` is one; the ADR names that file as the single module allowed to import opentelemetry |
| C02 | violation | violation | unclear | violation | Sound (core module importing opentelemetry directly) |
| C03 | violation | violation | unclear | violation | **Right for the wrong reason.** Applies the opentelemetry prohibition to a `sqlalchemy` import; the ADR says nothing about databases |
| C04 | violation | violation | justified | violation | Sound enough (direct calls between modules are not the decided style) |
| C05 | violation | violation | unclear | **justified** | **Wrong, in the dangerous direction.** Over-generalises "modular monolith" to permit the cross-module internal reference |
| C06 | justified | violation | unclear | justified | Right verdict, vague reason ("permits modular monoliths") |
| C07 | violation | violation | unclear | violation | Sound |

Verdicts correct: M6 as pipeline 5 of 7, M6 reading only 0 of 7, M7 5 of 7. **Read these numbers carefully:**
* M6 as pipeline says "violation" for all seven (the v1 matcher links the right ADR only for C01 and C02, which name the file), so its 5 of 7 equals the
  base rate: five of the seven cases are violations. **M7's 5 of 7 is the same number, so this study gives no evidence that M7 beats "always violation".**
* Only 3 of M7's 7 answers are correct for sound reasons (C02, C04, C07); C03 is correct by confusion and C06 with a vague reason. M7 found 1 of the 2
  justified cases and 4 of the 5 violations. One of its errors (C05) hides a real violation.
* **What it does show:** on real, long, multi-topic ADR text the extractor can misattribute scope (C01, C03) and over-generalise a style decision (C05).
  These are failures that the benchmark's short templated decisions never exposed, so the benchmark F1 (0.97) must not be quoted as expected performance on real ADRs.
* Seven hand-picked cases are a demonstration, not a rate. No confidence interval is meaningful.

M8's routing on the same seven (frozen code, no model; computed offline): C03 is routed to a structural violation without the model because the ADR is about
telemetry and does not mention a database library (the right answer for the right reason, where M7 was confused); C01 and C02 are scoped as described and
fail the `G_clear` gate (no permission or prohibition cue in the decision), so M8 would send them to the model; **C04 to C07 are scoped as "weak" only because
of a limitation of the frozen code**: the name-matching helper reduces a file path to the text after the last dot, which is right for `.py` and returns `cs` or
`java` for C# and Java files. The gates and the description-aware scope test therefore work on Python paths only (and the analysis pipeline's parser is
Python-only in any case). Not changed, because anything altered now would need a fresh confirmation; a v2.1 should split camelCase names and strip
any extension.

What the case study supports: real ADRs expose reading errors the benchmark did not (honest negative evidence); a grounding step that makes
the model quote the sentence it relies on (and code verify it names the right module) is the natural next fix; the gates' scope test helped on C03
but is Python-only. It does not support any claim about M7's accuracy on real ADRs.

## Finishing the real-ADR part (current state)

1. **Sample labelling:** two AI passes, then a team verification of all 60 rows (section "Human verification"). Labels of record: `annotation_sheet_verified.csv`. The blind 20-row check is optional.
2. **The 7 draft verdicts: human review done.** Anukriti Chauhan wrote verdicts for all 7 cases independently, **before seeing the draft `expected`
   column and before any model output** (self-reported), then compared them with the draft: **7 of 7 agree** (`cases_reviewed.csv`, columns
   `team_expected`, `team_reviewer`, `team_review_basis`). A separate AI review by Claude
   (columns `claude_expected`, `claude_confidence`, `claude_notes`) also agrees 7 of 7 but was not blind to the draft. Three-way agreement is
   therefore: builder's draft, blind human review, AI review. Because the human verdicts equal the draft, no verdict was changed. AI confidence
   was high for C01 and C02, medium-high for C05, medium for C03, C04, C06 and C07 (reasons in the file; C03's flagged rule is the builder's own
   and the import may be legitimate persistence code, so it is scored only as "the ADR grants no permission"; C04 and C06 are marked debatable).
3. **Run the model part: done 2026-11-22** (results above).
4. **Score:** `python -m experiments.real_adrs.case_study --cases ../datasets/real_adrs_case_study/cases_reviewed.csv --rescore <results.csv>`.
5. When reporting, give the case-study table with the provenance in one line: "verdicts drafted by the case builder, independently reviewed by a
   team member (Anukriti Chauhan) before any model output (7/7 agreement) and by an AI assistant (7/7)". Seven cases remain a demonstration, not a rate.

# Evidence-Guided Architecture Conformance Analysis

Detects where a codebase has drifted from its intended architecture, and decides *when
an LLM is actually needed* to tell a genuine violation from a justified exception.

```
repository ──► Tree-sitter parse ──► components + dependencies ──► rules ──► findings
                                                                              │
        Git history ──► when was it introduced? ────────────────┐             ▼
        ADRs / rules ──► what was intended? ────────────────────┼──► evidence bundle
        code structure ──► what does it actually do? ───────────┘             │
                                                                              ▼
                                               "Evidence sufficient?" ──yes──► direct verdict
                                                         │ no
                                                         ▼
                                          LLM EXTRACTS facts from the ADR (decision, date limit)
                                                         │
                                                         ▼
                                          code COMPUTES the verdict (date comparison with Git history)
```

Final-year Major Project (Research + Development). Research question: can architectural
intent, structural evidence and software-evolution history decide *when* semantic (LLM)
reasoning is necessary, trading detection quality against LLM cost?

### Results at a glance (Qwen2.5 7B; details and caveats in the docs named above)

| Data | Result |
|---|---|
| Hard tier, 216 fresh cases (seeds 11-13), pooled | F1: M7 **0.975** (0.955-0.990), M5 0.896, M3 0.892, M1 0.800, M6 (code-only reader) 0.588. M7 minus M5 = +0.079 (95% CI 0.042 to 0.121) at the same 171 calls; M5 matches M3 with 21% fewer calls |
| Held-out wording (blind), test split | F1: M7 0.974, **M6 0.973 with zero LLM calls**, M5 0.889, M3 0.857 |
| Date reasoning (scenario D, after the cut-off) | M5/M3 2 of 18 correct (they invent the date comparison); M7 18 of 18 (code compares) |

| Real ADRs (11 pre-2023 projects, 202 ADRs; 60 labelled: AI draft, verified by the team) | Dependency-governing ADRs: **3/60 clearly (5.0%, CI 1.7-13.7%), 10/60 at least partly (16.7%, CI 9.3-28.0%)**. The earlier single-pass hand-read gave 2/60 and 6/60; the verified labels are the ones of record. The code-only reader handled none of the 6 found in that first read. Verified row by row by the three team members (the sheet showed the AI draft beside each excerpt): `docs/REAL_ADRS.md`

**What this does and does not show.** An LLM adds value over a convention-based code reader only when ADR language is
irregular (hard tier); on templated and mildly paraphrased wording the code-only reader matches it at no cost. How
irregular real ADRs are is not answered by any synthetic benchmark here. The benchmark is generated by the project team,
one small quantised model was used, and M7 is weak on mixed ADRs that permit one module and forbid another (scenario M, 11 of 18).

Tests: **611 backend (5 skipped) + 111 frontend = 722 passing** (re-run 2026-11-22). Coverage was last measured before the M6/M7 and API integration work and has not been re-measured.
Unit tests use stub models, so they need no API key and no network.

## Quick start

```bash
# backend (Python 3.12, git must be installed — the evolution analyzer uses it)
cd backend
pip install -r requirements-dev.txt
uvicorn main:app --reload                       # http://localhost:8000/docs

# frontend
cd frontend
npm install
npm run dev                                     # http://localhost:5173  (proxies /api to :8000)
```

### Quick start with Docker (one command, no extra terminals)

```bash
docker compose up --build                  # backend :8000 + frontend :5173
docker compose --profile db up --build     # also starts PostgreSQL (set DATABASE_URL in .env, see .env.example)
```
Ollama stays on your host; the backend reaches it at `http://host.docker.internal:11434/v1`. Override `LLM_MODEL` etc. via `.env`. The repo is bind-mounted, so code edits reload live and the default `../datasets/...` paths work.

By default the API keeps runs in memory. Set `DATABASE_URL` (a PostgreSQL connection string) to store runs in PostgreSQL so they survive restarts; `/health` reports the backend in use.

Open the UI → **Run analysis** (defaults to the bundled demo repo) → Graph → Findings → open a
violation to see its structural, intent and evolution evidence and the policy's decision.
The **Evaluation** tab shows experiment results from `results/`.

### Choosing the escalation policy

```bash
export ESCALATION_POLICY=gated   # default: M8, the policy confirmed on fresh seeds, see docs/GATED_POLICY_RESULTS.md
export ESCALATION_POLICY=v1      # the earlier policy (M5/M7): every finding with an active relevant ADR goes to the model
```
`/health` reports the policy in use. Each finding is routed one of three ways (shown in the Decision panel): **resolved structurally**,
**resolved by code reading the ADR** (every readability check passed, no model), or **sent to the model** (the failed checks are named).
Escalated findings are resolved as in M7 (the model extracts, code computes). The stance-attribution check (`M8_gated_attr`, the scenario-M fix) **is applied** to every extraction by default: if a decision permits another module, a permission is accepted for the flagged module only when a sentence about that module grants it, otherwise the reading becomes a violation (the conservative direction). No extra model call. `ATTRIBUTION_CHECK=off` runs plain M8; `/health` reports the setting and the Decision panel shows "Whose permission" when the check ran. Its evidence is the synthetic mixed-decision scenario (18/18 on 216 fresh cases); it has not been shown on real mixed ADRs.
The gates only understand Python file names. With the primary ADR wording the gates read most ADRs, so the model path is easiest to demo with a
held-out-wording case (`--wording heldout` in the benchmark generator, see `docs/EXPERIMENTS.md`).

### Running the app locally with Ollama (Windows PowerShell)

Ollama must be running with a model pulled (the laptop demo uses the 3B: `ollama pull qwen2.5:3b-instruct`; check with `ollama list`). In the window that starts the backend:

```powershell
cd backend
$env:LLM_BASE_URL = "http://localhost:11434/v1"
$env:LLM_MODEL    = "qwen2.5:3b-instruct"
uvicorn main:app --reload          # http://localhost:8000/docs
```
Frontend, in a second window: `cd frontend; npm run dev` (http://localhost:5173). The `$env:` lines only apply to the window they were typed in. No API key is needed for Ollama; check the model is reachable with `curl http://localhost:11434/api/tags`. No database setup is needed either: runs are kept in memory unless `DATABASE_URL` is set.

Every measured result in this repository was produced with Qwen2.5 7B (Q4) on a Kaggle GPU; the 3B used for the local demo was not evaluated, so benchmark numbers must not be quoted for it. It is also more likely to return an unusable reply, in which case the app falls back to rule-based output and says so. If your machine runs the 7B comfortably (`ollama pull qwen2.5:7b-instruct`, then set `LLM_MODEL` to it), the demo matches the evaluated model. The first call on a CPU can take 10 to 60 seconds.

### Enabling the LLM (optional; only needed for semantic review)

```bash
export LLM_BASE_URL=http://localhost:11434/v1     # any OpenAI-compatible endpoint (Ollama, Gemini's
export LLM_MODEL=<model>                          #  compatibility endpoint, OpenRouter, ...)
export LLM_API_KEY=<key-if-needed>
export LLM_CACHE_PATH=../results/llm_cache.sqlite # reuse responses cached by the experiment runner
```
Without these the UI still shows all evidence and the policy's decision; only the "ask the model"
step reports how to configure one.

## Layout

```
backend/
  analysis/
    parser/        Tree-sitter parsers (Python); one subclass per language
    dependency/    scanning, import resolution, graph
    conformance/   deterministic rule engine
    evolution/     Git analyzer: when did this dependency appear?
    intent/        ADR parsing + relevance (architectural intent); reader.py = the code-only ADR reader (baseline M6)
    evidence/      one EvidenceBundle per finding
    policy/        escalation policy: is the evidence sufficient?
    semantic/      LLM client (retry/cache), prompts, review analyzer; extract.py = extract-then-compute (method M7)
  experiments/     benchmark generator (primary + held-out wordings), methods M1–M7 + ablations, metrics, runner, combine_runs (pools seeds), real_adrs/ (corpus fetch, profiling, agreement)
    real_repos/    import-linter contracts as intent: importer, evaluation, violation-lifecycle trace (see docs/REAL_REPOS.md)
  api/             FastAPI routes (analysis, findings, evidence, triage, experiments)
frontend/          React + Vite: Overview / Graph / Findings (evidence panels) / Evaluation
datasets/          sample-ecommerce demo repo; generated benchmark goes in datasets/benchmark/generated
docs/              EXPERIMENTS.md (how to run), ANALYSIS_PLAN.md and FALSE_PERMISSION_PLAN.md (pre-registrations + dated deviations log),
                   results write-ups (PRIMARY, HELDOUT_RESULTS, M7_CONFIRMATION, GATED_POLICY_RESULTS, FALSE_PERMISSION_RESULTS),
                   dataset notes (HARD_TIER, REAL_ADRS, REAL_REPOS), frozen_*_sha256.json (hash records checked by the run commands)
notebooks/         run_on_free_gpu.ipynb (used for every real-model run reported here, on Kaggle)
```

## Known limitations

- Python only; `import` dependencies only (no calls/inheritance).
- Import resolution matches dotted-path suffixes rather than real `sys.path` resolution; ambiguous
  basenames resolve to the shortest path (tested, documented in `module_index.py`).
- File renames are not followed by the evolution analyzer (flagged per finding).
- The benchmark is generated and authored by us; results show behaviour under controlled
  conditions, not accuracy on real repositories.
- Dependencies are direct Python imports between files; no indirect, cyclic or `required`/`conditional` rules.
- The ADR matcher can over-select on real ADR text (untested on real corpora); code comments are not used as evidence.
- Evolution analysis is per dependency (introduced/removed); it does not track repository-level violation trends, and history is truncated at 1000 commits.
- A date limit in an ADR must be a calendar date written in the decision text; relative limits ("within 30 days") are not handled.
- One small quantised model; no other model has been tried, and no language model has been run on real ADR text.
- Real ADRs rarely state dependency rules (5-17% of a 60-ADR sample, AI-drafted and team-verified), so ADR-based conformance applies to a minority of real ADRs.
